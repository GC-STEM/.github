# GC-STEM Repository Ecosystem

## GC-STEM/.github

The `GC-STEM/.github` repository must be **public** to provide default community health files.

### Default Community Health Files

Use this repository to maintain shared contribution instructions, support information, policies, and templates.

GitHub applies a supported default when a repository owned by GC-STEM does not supply its own corresponding file. This applies to both public and private repositories.

For supported files with multiple possible locations, GitHub searches in this order:

1. The `.github` directory
2. The repository root
3. The `docs` directory

GitHub checks the destination repository first, then uses the same location order in the default `.github` repository.

A repository-specific `CONTRIBUTING.md`, for example, overrides the shared contribution instructions. A repository with its own valid issue templates or issue-template configuration uses that configuration instead of the default `ISSUE_TEMPLATE` directory.

Shared defaults remain in this repository. They do not become files or commits in consuming repositories and are absent from their clones, packages, and downloads.

See [Creating a default community health file](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/creating-a-default-community-health-file).

To review a public repository's recommended community files, use its community profile checklist. See [About community profiles for public repositories](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/about-community-profiles-for-public-repositories).

## About security policies

A security policy explains how someone should privately report a suspected vulnerability.

Repository security advisories support private investigation and collaboration, followed by publication when the maintainers are ready to disclose the issue.

See:

- [Coordinated disclosure of security vulnerabilities](https://docs.github.com/en/code-security/concepts/vulnerability-reporting-and-management/coordinated-disclosure#about-reporting-and-disclosing-vulnerabilities-in-projects-on-github)
- [Repository security advisories](https://docs.github.com/en/code-security/concepts/vulnerability-reporting-and-management/repository-security-advisories)
- [GitHub's security policy for the documentation repository](https://github.com/github/docs/security/policy)

## Supported file types

The following files and templates can provide shared community guidance:

| **Community health file** | **Purpose and official documentation** |
| ------------------------- | -------------------------------------- |
| `ACCESSIBILITY.md` | Describe accessibility priorities, barriers, and reporting channels. See [Adding an accessibility page to your repository](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/adding-an-accessibility-page-to-your-repository). |
| `CODE_OF_CONDUCT.md` | Define expected conduct and the process for addressing violations. See [Adding a code of conduct to your project](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/adding-a-code-of-conduct-to-your-project). |
| `CONTRIBUTING.md` | Explain contribution requirements and procedures. See [Setting guidelines for repository contributors](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/setting-guidelines-for-repository-contributors). |
| Discussion category forms | Collect structured information for new discussions. See [Creating discussion category forms](https://docs.github.com/en/discussions/managing-discussions-for-your-community/creating-discussion-category-forms). |
| Issue and pull request templates and `config.yml` | Standardize issue reports and pull request descriptions. See [About issue and pull request templates](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/about-issue-and-pull-request-templates). Labels referenced by an issue template must exist in this `.github` repository and in each repository using the template. |
| `SECURITY.md` | Explain supported versions and vulnerability reporting procedures. See [Adding a security policy to your repository](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/add-security-policy). |
| `VULNERABILITY_REPORT.yml` or `VULNERABILITY_REPORT.yaml` | Customize the private vulnerability reporting form. See [Configuring private vulnerability reporting for a repository](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository#customizing-the-vulnerability-reporting-form). |
| `SUPPORT.md` | Direct users to the project's help channels. See [Adding support resources to your project](https://docs.github.com/en/communities/setting-up-your-project-for-healthy-contributions/adding-support-resources-to-your-project). |

A license cannot be inherited as a default community health file. Add the intended license to each individual repository so it accompanies clones, packages, and downloads.
